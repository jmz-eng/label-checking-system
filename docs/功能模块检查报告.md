## 项目结构与检查范围

项目为采血样品标签防错管理系统，前端采用 React 18、TypeScript、Vite、Ant Design，后端采用 Spring Boot、MyBatis-Plus、MySQL。页面由后端菜单动态注册；接口使用独立权限点控制访问。

主要业务为项目管理、采样任务生成、贴标绑定、操作核对、录入确认和扫码追溯，另有用户、菜单、权限、日志、公告管理。当前目录没有 Git 元数据。

本次修复集中在工作台。其他模块按源码检查记录问题，浏览器使用隔离接口数据验证页面和交互，不将其视为真实数据库或设备验收。未改动后端业务规则、现有数据库、部署配置或真实采样记录。

## 待修复问题

以下结论来自本次源码检查。未执行真实写操作验证，不应把静态检查误写成线上故障复现。P1 为影响防错、追溯或访问安全的问题，P2 为功能与使用问题。

### P1：扫码流程允许跳过步骤

- 位置：`backend/src/main/java/com/tagmanagement/service/SampleTaskService.java` 的 `verify`、`record`。
- `verify` 只排除作废状态，允许待贴标任务直接核对成功；`record` 只排除作废和待贴标，允许已绑定但未核对的任务直接录入。
- 已录入任务再次录入会覆盖录入人和录入时间，缺少幂等保护；并发操作使用普通 `updateById`，没有旧状态条件或版本校验。
- 建议按已确认业务流程收紧服务端状态转换，并通过条件更新和回归测试验证。工作台前端限制不能替代后端规则，独立扫码页和直接接口仍受影响。

### P1：异常记录可能因事务回滚丢失

- 位置：同上 `findTaskForScan`。
- 找不到标签时先插入失败记录，再抛出继承 `RuntimeException` 的 `BusinessException`。调用链位于默认 `@Transactional` 内，失败记录会随事务回滚。
- 结果：异常拦截页面的“标签不存在”分类可能缺少此类事件。部分无效状态异常也直接抛出，没有写入扫码记录。
- 建议由独立事务保存失败事件，并增加真实事务集成测试，验证返回错误后记录仍存在。

### P1：一维条码没有实际编码

- 位置：`frontend/src/components/LabelPreview.tsx` 的 `.barcode`，`frontend/src/styles.css` 的 `.barcode` 样式。
- 一维图形是固定重复渐变，所有任务图案相同；不是根据 `labelCode` 生成的可解码条码。下方文本还移除了连字符，与二维码载荷不同。
- 二维码使用真实 `labelCode`；本次大图修复只解决弹窗显示，不代表一维条码已经可扫描。
- 建议生成真实 Code 128 等指定码制，统一人眼可读编码，增加图像解码测试和实物打印扫码验收。

### P1：重置密码、退出后旧令牌未撤销

- 位置：`UserManagementService.resetPassword`、`TokenService`、`AuthInterceptor`、`frontend/src/stores/AuthContext.tsx`。
- 重置只更新密码哈希；令牌只包含用户和到期信息，鉴权不比对凭据版本。退出只清除本地存储，没有服务端撤销。
- 因此已签发令牌在用户仍启用且令牌未到期时可能继续使用。账号停用会被后端实时查询阻止，这是现有有效保护。
- 建议增加凭据版本或服务端会话记录，并验证重置、退出及停用后的旧凭据行为。

### P2：打印多个标签可能重叠，搜索后保留旧标签

- 位置：`LabelPreviewPage.tsx`、`styles.css` 的 `@media print`。
- 标签预览页同时渲染多个标签，打印样式让所有 `.label-preview` 可见并绝对定位到同一位置；“打印当前标签”没有限定打印目标。
- 搜索加载使用 `current ?? data[0]`，即使新结果没有旧任务，右侧仍保留旧标签，容易打印错误对象。
- 建议使用专用打印区域，只渲染已确认目标，并在搜索后重新校验选择。增加打印预览截图和选中标签校验。

### P2：菜单权限与依赖接口权限不一致

- 标签菜单要求 `label:view`，页面调用的任务接口要求 `sample:view`。
- 异常菜单要求 `exception:view`，页面调用的扫码记录接口要求 `record:view`。
- 报表菜单要求 `report:view`，页面还并行请求任务和扫码记录；缺少其中一项权限就导致整体加载失败。
- 工作台统计接口只有登录校验，没有独立业务权限注解，应明确哪些角色可以看到全局统计。
- 菜单、权限、公告页面部分写按钮没有前端权限判断，只有查看权限的用户会看到不能执行的动作。后端仍有权限校验，不能据此断言已发生越权写入。
- 建议统一页面与接口授权设计，增加按最小权限组合运行的页面测试。

### P2：统计报表的通过率和异常率口径不正确

- 位置：`WorkbenchService.summary`、`StatisticsReportPage.tsx`。
- 核对通过数、核对总数实际统计扫码记录次数，却除以任务总数；同一任务重复操作会放大比例，可能超过 100%。异常记录也用任务总数作分母。
- 本次工作台按接口真实含义显示累计次数，并移除误导百分比；报表页和接口比例仍需另行修正。
- 建议分别定义“核对通过次数 / 核对次数”和“已核对任务数 / 总任务数”，明确时间范围及任务去重口径。

### P2：菜单结构缺少服务端有效性检查

- 位置：`MenuService.fillMenu`、`buildTree`。
- 保存时直接接受父菜单 ID，没有校验父级存在、自引用或祖先环。错误结构可能使菜单脱离根节点，从用户菜单树中消失。
- 建议保存前验证父子关系和路由有效性，覆盖父级不存在、自引用、环形依赖与重复路径。

### P2：加载失败可能显示无异常，窄屏无模块导航

- 异常拦截页初始记录为空，接口失败后仍按空记录展示“当前无异常拦截”；应区分加载中、加载失败和确实无记录。
- 小于 760px 时全局样式隐藏侧栏，但 `AppShell` 没有替代导航入口，手机用户难以切换模块。
- 建议补全错误状态和移动端菜单，并分别进行异常接口、手机尺寸验证。

### P2：公告编辑后新增可能残留上次内容

- 位置：`NoticeManagementPage.handleOpen`。
- 打开新增表单时只设置类型和发布状态，没有重置标题、内容；编辑后再次新增可能携带原公告内容。
- 建议每次打开先重置表单，再填入本次数据，补充编辑关闭后新增的回归测试。

### P1：公告保存接口可绕过单独的发布权限

- 位置：`NoticeController.create/update/publish`、`NoticeService.fillNotice`。
- 独立发布接口要求 `notice:publish`，但新增和编辑只要求 `notice:create` / `notice:update`，请求中的 `publishStatus=PUBLISHED` 又会被服务直接采用。
- 结果：拥有新增或编辑权限但没有发布权限的角色，仍可通过保存操作将公告设为已发布。该结论由调用链静态确认，本次未实际发布公告。
- 建议在服务端集中校验发布状态转换，所有可触发发布的入口执行同一权限检查，并覆盖自定义角色测试。

## 建议处理顺序

1. 先修服务端状态转换、失败留痕和会话撤销。
2. 补齐真实条码和单标签打印，完成实物扫码验收。
3. 统一权限组合与统计口径。
4. 处理菜单结构校验、公告残留、错误状态和移动端导航。
